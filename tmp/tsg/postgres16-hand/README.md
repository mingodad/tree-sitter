# postgres16-hand — a hand-fixed copy of the postgres16 grammar

`postgres16/check.sh` cannot run: it regenerates the grammar from
`../postgres16.g` and fails when the result is not the checked-in
`postgres16/grammar.tsg`. The two now disagree because the translator was fixed
after that copy was taken (`bison_flex/translate` gained the flex `\NNN` escape
fix), and the checked-in copy predates the nullable-rule → EBNF rewrite. This
directory is the translation brought forward **by hand**, so the grammar can
still be built and parsed while that decision is pending.

It is not a replacement for `postgres16/`. Nothing here is regenerated by a
script that also rewrites the checked-in copy; `build.sh` only compiles what is
in `grammar.tsg`.

## Run it

```sh
./postgres16-hand/build.sh                       # parses ../postgres16/sql_basic.sql
./postgres16-hand/build.sh path/to/other.sql
```

It writes `.build/` (grammar.json, parser.c, pg.dylib, tree.log) and prints one
line:

```
ok   5319 states, 26922340 parser.c bytes, 301 tree lines, 0 ERROR/MISSING
```

Needs `target/debug/tsg` and `bin/tree-sitter` (override with `TSG=` / `TS=`).

## What was changed by hand

`grammar.tsg` is the output of

```sh
g2tsg postgres16.g -o postgres16-hand/grammar.tsg --name postgres \
    --title "…" --header postgres16/header.txt \
    --conflicts postgres16-hand/conflicts.txt --bodies postgres16/bodies.txt
```

— the same flags `postgres16/check.sh` uses — and the only hand-written input is
`conflicts.txt`, which differs from `postgres16/conflicts.txt` in five entries.
`opt_frame_clause` no longer exists as a rule (the nullable rewrite inlines it
into `frame_bound`), so the one whitelist line naming it had to be renamed, and
four conflicts that the rewrite exposes have to be whitelisted:

    - opt_frame_clause unreserved_keyword
    + frame_bound unreserved_keyword
    + expr_list
    + func_arg_list
    + json_predicate_type_constraint
    + joined_table

All four additions are load-bearing: removing any one of them makes
`tree-sitter generate --lalr` refuse with that sequence unresolved. Details and
the reasoning are in `conflicts.txt`.

## What it produces, next to the checked-in grammar

| | checked-in `postgres16/grammar.tsg` | this copy |
|---|---|---|
| states | 4853 | 5319 |
| `parser.c` | 24,792,142 bytes | 26,922,340 bytes |
| `sql_basic.sql` | 299 tree lines, 0 `ERROR`/`MISSING` | 301 tree lines, 0 `ERROR`/`MISSING` |

Both accept the sample; the trees are **not identical** — 182 lines of diff, all
inside `target_list`/`a_expr` nesting. That is the nullable → EBNF rewrite
choosing right recursion where the checked-in copy spells the rules out
left-recursively, not a conflict-resolution difference. It is the part a human
has to bless before `postgres16/grammar.tsg` is regenerated: the shape is what
downstream queries and node counts are written against.

## Status

- `bin/g2tsg` is still the pre-fix binary; `grammar.tsg` here was produced by a
  scratch build of `bison_flex/translate` after `src/flex.rs` was fixed
  (`(b'0'..b'7')` → `(b'0'..=b'7')`, with two tests in `src/tests.rs`).
  Rebuilding `bin/g2tsg` will change `postgres16/` and `antlr/` output, so it is
  a decision, not a cleanup.
- The rest of the `.g` corpus is unaffected: the escape bug only shows up in
  patterns that contain an octal escape with a `7` in it.
